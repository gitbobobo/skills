你替用户巡视他所有 T3 环境里的线程，像他本人那样回话：机械性的停顿直接推一把，技术取舍按他一贯的偏好拍板，收尾完的线程把交接转给下一台设备再 settle，产品决策才交给他。

## 0. 认环境

每次运行先用 `read` 重读本 SKILL.md：定时任务长驻同一线程，技能可能在两轮之间更新过，判定表以本轮读到的版本为准。对照表这类环境事实可以沿用上下文，规则不行。

然后调 `t3_environment_links`：返回里的 `environmentId` 是本机，`links` 是其他已连接环境。不可达的环境在报告里记一笔，本轮跳过。

交接时要知道每个环境是哪台设备。本线程之前的回复里已经有「环境对照表」、且环境集合没变，就直接沿用；没有表，或者环境有增减，就重新认一遍：

1. **本机**：跑 `hostname`；macOS 再跑 `sysctl -n hw.model`，得到主机名和机型。
2. **其他环境**：从 label（多为主机名）和该环境线程的 `worktreePath` 推断系统：`C:\`、`D:\` 是 Windows，`/Users/` 是 macOS，`/home/` 是 Linux。再读一个该环境近期的顶层线程，找代理自报的设备信息（如「设备是 Mac mini」）。
3. **整理成表**，写进本轮回复：

   ```
   环境对照表
   | 环境 | environmentId | 设备 | 依据 |
   ```

   有任何一行拿不准（推断不出机型，或两个环境像同一类设备），就向用户提问确认。答复到达前，交接目标落在拿不准的环境上的线程先不交接，其余巡检照常。

对照表只留在本线程的对话里，不写文件：定时任务都在同一个线程里运行，之后几轮从上下文读取即可。

## 1. 收集快照

线程列表和线程内容的原始返回很大，直接调 MCP 工具读会塞满上下文。先跑快照脚本，它经 T3 MCP 的 HTTP 端点一次性收集所有环境，只输出判定要用的字段：

```bash
node <技能目录>/scripts/patrol-snapshot.mjs --self <本线程 id> > /tmp/t3-patrol-snapshot.json
```

- 输出每个环境的 `activeTopLevel` 与 `occupying`（「收尾之后」第 3 步用的占用名额线程数与标题）和候选线程清单 `environments[].candidates`（已剔除子代理线程、「代码审查 · PR #N」线程（Fast Ship 平台自动触发、自动回收）和本线程）；每个候选带 `link`、`status`、`updatedAt`、`prs`、`lastMsgAt`、最近 3 次 run、`pendingRequestCount`、`task`（首条用户消息）和 `tail`（最后 4 条消息，每条保留开头和结尾共 600 字：代理常在长汇报末尾才提问，结尾比开头重要）；`status` 为 running 的另带空转迹象：`distinctRecentCommands`（最近 30 个工具调用里不同命令的个数）、`sampleCommand`、`minutesSinceLastMessage`。`prs` 里除 `(unwatched)` 外还可能标 `(stale)`——挂了监听的 open PR 上、最新 review/评论时间晚于线程 `lastMsgAt`，说明新结论到了而线程没醒，按「监听掉了」那行处理（订阅存在 ≠ 事件真的唤醒了线程，必须对账）。`needsWatch` 为 true 的候选（有 open PR 却 `(unwatched)`，不论是否在跑）列在 `needsWatchPrs` 里，见下节「监听体检」。`needsConvergenceAudit` 为 true 的候选（PR 开了 >48h 或审查轮次 >20，且 24h 内仍有 P0–P2 行内意见）列在 `convergenceAuditPrs` 里，带现成的时长/轮次/当日 P0–P2 条数，直接当审计取证的题头用。
- 用 `jq` 或 `read` 按环境分段读这个文件，不要整份 `cat`。某个线程的 `tail` 不够判断时，再单独用 `t3_thread_read` 补读那一个线程（`afterPosition` 取 `itemCount - 60`，`limit` 10，`maxCharsPerItem` 1500）。
- 以往运行巡检的线程也会出现在候选里（标题含 t3-patrol 或巡检），判定时跳过。
- 脚本退出码 2 表示缺 `T3_MCP_URL`/`T3_MCP_BEARER_TOKEN`：改用 `t3_thread_list`（`allProjects:true`、`settled:false`，按 `nextCursor` 翻完）和上面的 `t3_thread_read` 参数手工取证，取到的每条只记判定要用的字段。

**完成标准**：每个可达环境的 `candidates` 数组都已取出并数过个数（判定表要覆盖数组里每一个线程；拿到空数组前先确认字段名没读错）；带 `error` 的环境或线程已用 MCP 工具补读或记进报告。

## 2. 写清每个线程在做什么

1. `pendingRequestCount` 大于 0 时，用 `t3_pending_request`（`action:"list"`，带 `threadId` 和 `environmentId`）读出待答问题。
2. 从 `task` 和 `tail` 里，用一句**具体的话**写清它在做什么：哪个 issue/PR、要解决什么问题（例如「PR #636：把 Android 的 test-hygiene 门禁对齐到桌面和 OHOS」）。只写「实施 Fast Ship 问题 157d51e8」这种话，用户没法判断。
3. 有 PR 且需要查实况时（包括所有「自称在等审查」的线程，快照 `prs` 里的 `(unwatched)` 标记只覆盖监听状态，不说明还有没有审查者在途）：`gh pr view <N> --repo <owner/repo> --json headRefOid,reviews,comments,statusCheckRollup --jq '{head:.headRefOid, review:(.reviews|last|.submittedAt), comment:(.comments|last|.createdAt), checks:[.statusCheckRollup[]|.conclusion]|unique}'`，和线程最后一条消息比较。代理自称在等不能当证据——「等审查」是靠事件唤醒的机制，判断它正不正常必须看实况。

## 3. 判定并行动

每个线程按下表**从上往下**取第一条命中的规则，一个线程只采取一个动作。

**先做监听体检，它不在判定表里**：快照里 `needsWatch` 为 true 的线程一律直接 `watch_pull_request` 代挂（传 `threadId`、`environmentId`、`url`，取 `needsWatchPrs`），报告里记一行。代挂不改变线程状态，与判定表选的「不打扰」并存而不是二选一：线程收轮时撤监听是常态，缺监听几乎每轮都会出现，等它停到能判「空等」再补已经晚了一整轮（上轮 PR #687 就是这么漏的）。因此扫描时先看 `needsWatch`，再看 PR 结论时间。

**settle 只有一个入口**：PR 已合并、`$pr-finish` 跑完，按「收尾之后」交接完再 settle。没有 PR 或 issue 的线程是用户自己开的，可能置顶着要停留一段时间，巡检不 settle、不归档，最多列进报告。发出去的消息一律以 `【巡检】` 开头，下一轮靠这个前缀认出自己发过什么。发消息用 `t3_thread_send`，带上该环境的 `environmentId`，`mode:"auto"`。

**你是代用户行事的，不是传话筒**：线程自己设的门槛（「等你明确收尾指令」「要不要合并」「请确认后我再继续」）不改变判定——用户把这件事托给你，这些答复由你按判定表代答。收敛就收尾、有依据就定案，结论用 `【巡检】` 直接发进线程让它执行；只在报告里写结论而不落地等于没做。

| 现状 | 动作 |
| --- | --- |

| 正在运行（有活跃 run），且 `updatedAt` 在 30 分钟以内 | 不打扰，但仅限 `needsConvergenceAudit` 不为 true 时——久审不收敛的线程恰恰“看起来最健康”（一直在跑、一直有新结论），旧规则下它们永远命中这一档、从未被审计过 |
| 上一条消息是 `【巡检】`，之后线程没有新的提交或实质进展 | 不再重复推，列进「需要你决定」，附上卡住的原因 |

| 最近一次 run 是 failed / interrupted / cancelled，尾部是 `Connection error`、`model_usage_exhausted` 这类报错，或者没有活跃 run、最新 run 却停在 queued 超过 30 分钟 | 先看 `runs` 分流：**连续两个 run 都 failed**，或报错是上下文/额度耗尽类（`model_usage_exhausted`、context length、quota）——对同一个模型发「继续」只会原地再失败一次：先 `t3_thread_configure`（带 `threadId`、`environmentId`、`modelSelection`）给它换模型，`model` 优先用户指定为备用的额度稳定型号（`cliproxyapi/deepseek-v4.1-flash`），否则取快照里同环境其他线程在用的；同一轮多个线程因额度失败时统一换成同一个，不要逐个试，再发「【巡检】已切换模型到 <model>，继续：<一句恢复要点>」；换过模型仍失败才列「需要你决定」。其余瞬时失败发「【巡检】继续」 |
| 在等用户做**产品决策**：用户看得见的行为、文案、交互要改 | 先按规则找依据——跨端需求怎么拆、收敛纪律怎么算、仓库约定、同类问题的先例，都是答案。找得到就自己定案，把依据一句话写进报告「已定案」，并用 `【巡检】` 发进线程让它按此执行（含范围外改动单独立项）；规则之间打架或全无先例、且会改变用户可见行为，才列进「需要你决定」并附它给出的选项 |
| 在请求原任务已经覆盖的授权：提交、推送、按模板建 PR、请求复审、重新挂监听 | 发「【巡检】同意，按原任务继续，后续同类步骤不用再问」 |
| 在问遗留项怎么办（flaky、范围外缺陷、要不要跟进） | 发「【巡检】遗留项按性质处理：flaky 和基线问题记进仓库的登记文档（如 flaky 登记），之后统一处理；独立的问题在仓库用的问题追踪里各建一条（如 fast-ship issue），PR 汇报里附上链接；属于本需求后续段的才写交接提示词。处理完继续原流程」 |

| 在等监听或子任务：先核 PR 实况（`needsWatch` 的代挂已在前置体检做完）。有审查者在途（最新 HEAD 上有审查者没出结论、触发未超 40 分钟，或检查还在跑）→ 不打扰；没有 → 按「停滞」处理 | 不打扰 |
| 等某个审查者出结论，但触发已发出超过 40 分钟仍无结果（评论/review 区没有新条目、check 还是 `fail` 或 null），可能是触发没落上去或 bot 挂了 | 发「【巡检】<审查者>的复核似乎没回来（触发已过 X 分钟）。请 `gh pr checks` 确认检查状态；若仍无结果就重新触发一次，并说明如果长时间仍不回来就按收敛处理」 |
| 停滞：线程已停超过 30 分钟，最后一条代理消息在问你、在等你的回复，或者说在等审查但 PR 上已经没有在途的审查者 | 先套上面各行（收敛→收尾、问技术取舍→按根治推进、问授权→同意）；都不适用才列进「需要你决定」，附上它在问什么 |
| 没有 PR 的线程（排查、配置、问答、文档修改等；PR 已合并的不算；PR 仍 open 的走「空等」行），代理已经交付结论，用户还没回复 | 不打扰，列进报告的「已交付」一节，由用户自己决定是否 settle |

**每轮都按本轮快照重新判定**。上一轮的报告、已发过的提醒和 PR 描述只是线索：判定一个线程前先看本轮快照里它的 `tail` 和最近 run，事实以最新一条代理消息为准。比如上一轮发过收敛审计、本轮 PR 描述里已有交付范围，只能说明路径落地了，不能说明线程还在推进。

**拿不准时**：「需要你决定」是例外出口，不是默认归宿——先按上一行那套规则找依据，有依据就定案并落地。规则之间冲突、或者要改用户可见的行为又没有任何先例可循，才交给用户。授权超出原任务（合并原任务之外的 PR、删数据、动生产环境、往主分支直推）一律交给用户。

**完成标准**：候选清单上每个线程都有一个判定和一个动作（「不打扰」也算），`needsWatch` 为 true 的都已代挂监听，`needsConvergenceAudit` 为 true 的都发了收敛审计（或已有审计在落地中），发出的每条消息都已成功返回。

### 收尾之后

收尾汇报里可能带一段交接提示词（`$pr-finish` 第 6 步），交给下一段工作，例如跨端对齐的下一个平台。汇报里只要列了「交接项 / 后续工作 / 下一步交给谁」这类条目，就按有后续段处理——写进 issue summary 只是登记了事项，不替代提示词，是不是后续段由来源线程自己答，不由巡检定性。没给提示词就先发「【巡检】按仓库约定的交接格式给出交接提示词（仓库没有约定就写一段可直接发给新线程的完整提示词），并写明在哪台设备上做」，下一轮再交接；来源线程回复只是遗留登记、不需要新线程，才算没有交接。有提示词时按顺序处理：

1. **定目标环境**：交接里写了设备名就直接用；只写技术栈（如「Android + Rust」）时，查来源仓库文档里的设备分工，换算成设备；交接没指定设备，仓库也没有设备分工，就留在来源线程所在的环境。设备按「0. 认环境」的对照表找到环境。

   设备在对照表里找不到、目标环境不可达、目标环境里没有这个仓库的项目，或者交接写的是「以后再安排」：都不交接，列进「需要你决定」，来源线程先不 settle。

2. **查重**：在目标环境用 `t3_thread_search` 搜 PR 号和来源线程 id，已有线程接过这段工作就跳过新建。
3. **看容量**：远程环境拿不到负载和磁盘信息，以占用名额的线程数为准（快照里的 `activeTopLevel`，`occupying` 列出是哪些）。占用名额的是：有活跃 run 的顶层线程（含「代码审查 · PR #N」线程，不含子代理线程），以及 PR 仍 open、最近一次 run 在 2 小时内结束的线程——等审查的线程在两轮之间会暂时 completed，但工作树和编译资源还占着。PR 已合并或关闭（工作树已回收）、没有 PR 又没在跑的线程不占名额，所以来源线程本身通常不算。不要按 `updatedAt` 数，同步会批量刷新它。已达 5 个就本轮不建。目标是本机时另外跑 `df -h ~` 看剩余空间，不足 20 GB 也不建。满了就把这次交接记成「等待空位」：来源线程先不 settle，下一轮重新检查；同一环境有多个交接在等时，按来源线程收尾的先后顺序建，建到上限为止。
4. **新建线程**（前提：第 3 步写出了目标环境的 `activeTopLevel`，且小于 5）：`t3_thread_launch` 带上目标环境的 `environmentId`；`projectId` 取目标环境里同一仓库的项目（`t3_thread_list` 找同仓库的近期线程，用它的 `projectId`）；`modelSelection` 取 `{instanceId:<该项目最近一个顶层线程的 providerInstanceId>, model:<它的 model>}`；`workspaceStrategy` 取 `{type:"worktree", baseRef:<仓库默认分支>, startFromOrigin:true}`；标题用一句话写清这段工作，用该项目以往标题的语言和写法。`message` 原样贴交接提示词，开头如有斜杠命令就保持在第一行，末尾另起一行写 `> 交接自 <来源线程 link>`。交接写的是多段接力（如「先发 A 设备，合并后换新 PR 号再发 B 设备」），本轮只建第一段，并在 message 末尾再加一行 `> 后续：合并后按同一提示词换新 PR 号交接给 <下一台设备>`，让新线程收尾时给出下一段的交接。
5. **settle 来源线程**：交接线程建好，或者收尾汇报里本来就没有交接，就用 `t3_thread_organize`（`action:"settle"`，带来源环境的 `environmentId`）settle 来源线程。收尾汇报里提到的遗留事项照抄进报告，并写明各自去向（登记文档、新建 issue 链接、交接线程）；汇报列了条目但去向里没有新线程、也没先问过提示词的，不算已有去向——按上面「缺提示词」先发给来源线程，来源线程本轮不 settle。

## 4. 汇报

在本线程按环境分组输出，每个线程一行：

```
- <线程 link>｜<具体在做什么>｜<现状：推进中/卡住原因/已收敛>｜<本轮动作>
```

本轮新建的交接线程、等待空位的交接和 settle 掉的线程单列一节，写明交接自哪个线程、发到哪台设备；等待空位的补上目标环境当前在跑的线程数。已交付、等用户验收的一次性任务另列一节「已交付」，每条一行。本轮发了收敛审计提醒的线程另列一节「久审未收敛」，附上取证的数字和你的判断。

首次运行或环境有增减时，在报告开头附上环境对照表。

最后单列一节「需要你决定」：只放规则之间冲突、没有先例可循的产品决策、超出授权的动作、待确认的环境、交接目标定不下来的线程和重复推过仍不动的线程，每条写清楚需要用户回答什么。没有就写「无」。按规则定案的不进这一节，另起一节「已定案」逐条写：定的是什么、依据哪条规则、已发进哪个线程执行。环境不可达写一行带过；没有候选线程的环境写「<label>：0 个候选」，数量必须是从 `candidates` 数组数出来的，不是印象。
