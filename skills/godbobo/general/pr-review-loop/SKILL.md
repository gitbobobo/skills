---
name: pr-review-loop
description: PR 推送并请求复审后，自动等待审查 bot 与 CI、处理新意见、再次请求复审，直到收敛。
---

请求复审后持续跟进至收敛。等待统一跑等待脚本按轮检查；一轮返回不代表任务已完成。

## 跟进入口

1. 先读取当前 PR 的最新评论、审查结果和最新 HEAD 的检查状态，恢复工作树外的跨轮账本。可用现有脚本做一次快照：

   ```bash
   node <技能目录>/scripts/pr-review-wait.mjs --timeout 0 --peek
   ```

   `--peek` 不消耗未读记录，按账本处理已处理/未处理意见；先处理已有事项再进入等待。快照与每一轮都核对最新 headRefOid，旧提交上的通过不能代替最新提交的检查与审查。
2. 按「收敛规则」判断 → 修复 → 核验或补跑相关检查 → 在已有提交/推送授权范围内提交推送 → 回复 → 按 PR 模板请求本轮未通过的审查者。需要额外授权时先完成可审阅的修复，再交回用户。
3. 后台运行等待脚本等下一轮（终端后台执行并保存日志，或 `run-watch`）：

   ```bash
   run-watch start <本PR唯一名称> -- node <技能目录>/scripts/pr-review-wait.mjs
   ```

   查看同一任务的日志与退出状态，不重复启动仍在运行的脚本。脚本默认等满 30 分钟（覆盖一个无响应窗口），退出码 `2` 表示还在等，有意见先处理，无意见再运行一轮；`0` 表示回应齐全，处理意见后检查结束条件；`1` 表示错误，先排查。不要自写 sleep 循环。

脚本在对话中断后恢复时首次加 `--reset`，结合账本避免漏处理或重复回复。脚本提示某审查者无响应（请求后 30 分钟仍无回应）时，重新请求一次；再次超过同一窗口无响应就不再等它，结束时说明。

每轮等待保留 PR URL、最新 HEAD、账本路径、未回应审查者、请求时间与重试次数，供下一轮直接续跑。结束跟进、因产品决策暂停、用户停止或交回用户前，停掉仍在运行的等待脚本。

## 收敛规则

**意见识别不看作者。**Code Bot 等 bot 借本账号 token 发结论，人类同事也可能用任意账号评论——所有非空评论都会进新意见列表；只有自己带 `<!-- pr-review-loop:reply -->` 标记的评论被排除（见「回复」）。

处理本轮新意见之前，先把它们归并分桶，再按桶回复：

| 桶 | 含义 | 回复动作 |
| --- | --- | --- |
| Act on | 影响正确性、安全或可维护性的真实问题 | 修 → 跑本次改动相关检查 → 回复修法和验证结果 → 重新请求这个审查者 |
| Consider | 说得对，但本 PR 不值得做 | 回复「有道理，本 PR 不做，理由 X」，**不**重新请求 |
| Noted | 技术上成立但不可行动（依赖上下文、过早优化） | 简短确认，不改 |
| Dismissed | 错的、吹毛求疵的、缺上下文的 | 回复驳回理由并给依据 |

**云端 bot 的一致性要降权。**多个审查者独立提出同一件事通常是高信号，但前提是它们看了同一份输入。PR 上的云端 bot（Code Bot、codex、Devin 等）输入并不相同——有的读了 PR 描述，有的只看 diff——所以「两个 bot 都提了 X」的置信度低于同输入的多模型审查。记录每条意见是谁提的，但不要让提的条数直接决定它进哪个桶。

**跨轮账本。**复审是多轮的，账本必须跨轮累积。写成一个 TSV，放在工作树之外（仓库约定不允许把临时文件留在工作树里），列为：`轮次 / 审查者 / 意见摘要 / 桶 / 理由 / 回复链接 / 本轮状态`。`pr-review-wait.mjs` 只打印未读意见，账本负责记住旧意见是怎么判的。

**Dismissed 跨轮复用。**一条意见在上一轮已被 Dismissed，下一轮另一个审查者又提同样的，引用上一轮的驳回理由和那条回复的链接，不要重新辩论一遍。

## 回复

脚本在每条新意见下面打印了「回复：」命令，照着用，把 `<回复文件>` 换成回复正文的文件路径。正文先写进 UTF-8 无 BOM 的临时文件，不要把中文内联在命令里。

- 行内意见：`gh api repos/<repo>/pulls/<n>/comments -X POST -F in_reply_to=<线程第一条评论的 id> -f body="$(cat '<回复文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"`
- 顶层评论、审查总结和 Code Bot 结论：`gh api repos/<repo>/issues/<n>/comments -X POST -f body="$(cat '<回复文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"`，正文开头引用被回复的意见或附上它的链接。

**自己发的每条评论末尾都要带 `<!-- pr-review-loop:reply -->` 标记**（HTML 注释，渲染后不可见）——回复、处置总结、更正都一样。监控脚本不按作者过滤，不带标记的自己评论会在下一轮被当作新意见回收一次。打印的回复命令已自动附加标记；手写命令（或 Windows 下 `$(cat …)` 不可用）时把标记写进回复文件末尾，再用 `-F body=@<回复文件>` 提交。

不要对任何评论执行 `PATCH` 或 `DELETE`，自己账号发的也不行。Code Bot 和 agent 用的是同一个 GitHub 账号，GitHub 不会拦，改错了就会覆盖审查结论。回复发错了就再发一条更正，不要改原评论。修改 PR 描述用 `gh pr edit`，不受这条限制。

## 暂停

- 遇到需要产品决策的意见，停下来问用户。

## 结束

所有审查者已回应（或已按上面的规则放弃等待），最新提交上没有未处理的有效意见，CI 通过：

1. 停掉仍在运行的等待脚本。
2. 勾选 PR 描述中「审查意见处理」的待办项。
3. 向用户简短汇报：共几轮；修了什么；哪些意见没改、理由是什么；哪个审查者无响应。
4. 不要合并 PR，等用户指令。
