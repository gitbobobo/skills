name: pr-review-loop
description: PR 推送并请求复审后，持续监听审查 bot 与 CI、处理新意见、再次请求复审，直到收敛。
---

请求复审后持续跟进至收敛。处理完一轮后保持对最新审查意见与检查状态的监听；一轮返回不代表任务已完成。

## 跟进入口

1. 先读取当前 PR 的最新评论、审查结果和最新 HEAD 的检查状态，恢复工作树外的跨轮账本。快照与每一轮都核对最新 headRefOid，旧提交上的通过不能代替最新提交的检查与审查。读评论/意见列表记得带 `--paginate`——不带只回最旧 30 条，评论多的 PR 新意见永远不可见。
2. 按「收敛规则」判断 → 修复 → 核验或补跑相关检查 → 在已有提交/推送授权范围内提交推送 → 回复 → 按 PR 模板请求本轮未通过的审查者。需要额外授权时先完成可审阅的修复，再交回用户。

   推送含可见 UI 改动的提交前：先重拍受影响界面、上传、`gh pr edit` 更新 PR 描述中的截图链接，再推送。Code Bot 在 push 时触发审查、读的是当时的描述——先推后改，它按旧图审，会对已修问题再开一轮。上传前先打开图片，确认不是过渡帧或旧布局。
3. 本轮处理完后继续监听最新审查意见与检查状态，新事件到达即回到第 1 步做快照。用你所在环境原生的 PR 监听手段，结束本轮等事件；不要自写轮询或 `sleep` 循环占着运行位。
4. 某审查者在请求后约 30 分钟仍无回应，重新请求一次；再次超过同一窗口仍无响应就不再等它，结束时说明。借本账号身份发结论的 bot 可能在你的监听手段里不产生事件，等不到时按同一条无响应规则处理。

结束跟进、因产品决策暂停、用户停止或交回用户前，撤掉仍在运行的监听。

## 收敛规则

**意见识别不看作者。**Code Bot 等 bot 借本账号 token 发结论，人类同事也可能用任意账号评论——所有非空评论都会进新意见列表；只有自己带 `<!-- pr-review-loop:reply -->` 标记的评论被排除（见「回复」）。

处理本轮新意见之前，先把它们归并分桶，再按桶回复：

| 桶 | 含义 | 回复动作 |
| --- | --- | --- |
| Act on | 影响正确性、安全或可维护性的真实问题 | 修 → 跑本次改动相关检查 → 回复修法和验证结果 → 重新请求这个审查者 |
| Consider | 说得对，但本 PR 不值得做 | 回复「有道理，本 PR 不做，理由 X」，**不**重新请求 |
| Noted | 技术上成立但不可行动（依赖上下文、过早优化） | 简短确认，不改 |
| Dismissed | 错的、吹毛求疵的、缺上下文的 | 回复驳回理由并给依据 |

**云端 bot 的一致性要降权。**多个审查者独立提出同一件事通常是高信号，但前提是它们看了同一份输入。PR 上的云端 bot（Code Bot、codex、Devin 等）输入并不相同——有的读了 PR 描述，有的只看 diff——所以「两个 bot 都提了 X」的置信度低于同输入的多模型审查。记录每条意见是谁提的，但不要让提的条数直接决定它进哪个桶。

**跨轮账本。**复审是多轮的，账本必须跨轮累积。写成一个 TSV，放在工作树之外（仓库约定不允许把临时文件留在工作树里），列为：`轮次 / 审查者 / 意见摘要 / 桶 / 理由 / 回复链接 / 本轮状态`。已处理的意见以账本为准，每轮快照时与最新评论对账，不要靠监听事件的计数。

**Dismissed 跨轮复用。**一条意见在上一轮已被 Dismissed，下一轮另一个审查者又提同样的，引用上一轮的驳回理由和那条回复的链接，不要重新辩论一遍。

**收敛不了就升级。**同一子系统在修复后的新提交上连续约 3 轮冒出新的 P0/P1，说明打地鼠修的是症状不是方向：停下跟进循环，调 `$code-review-panel` 对整份 diff 做方向审计——剩余问题，以及实现方向本身是否成立——然后自主决定收敛路径：继续修、立项重构、或回报用户。

## 回复

回复正文先写进 UTF-8 无 BOM 的临时文件，不要把中文内联在命令里。

- 行内意见：`gh api repos/<repo>/pulls/<n>/comments -X POST -F in_reply_to=<线程第一条评论的 id> -f body="$(cat '<回复文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"`
- 顶层评论、审查总结和 bot 结论：`gh api repos/<repo>/issues/<n>/comments -X POST -f body="$(cat '<回复文件>'; printf '\n\n<!-- pr-review-loop:reply -->')"`，正文开头引用被回复的意见或附上它的链接。

**自己发的每条评论末尾都要带 `<!-- pr-review-loop:reply -->` 标记**（HTML 注释，渲染后不可见）——回复、处置总结、更正都一样。不带标记的自己评论会在下一轮被当作新意见回收一次。Windows 下 `$(cat …)` 不可用时把标记写进回复文件末尾，再用 `-F body=@<回复文件>` 提交。

不要对任何评论执行 `PATCH` 或 `DELETE`，自己账号发的也不行。Code Bot 和 agent 用的是同一个 GitHub 账号，GitHub 不会拦，改错了就会覆盖审查结论。回复发错了就再发一条更正，不要改原评论。修改 PR 描述用 `gh pr edit`，不受这条限制。

## 暂停

- 遇到需要产品决策的意见，停下来问用户。

## 结束

所有审查者已回应（或已按上面的规则放弃等待），最新提交上没有未处理的有效意见，CI 通过：

1. 撤掉仍在运行的监听。
2. 勾选 PR 描述中「审查意见处理」的待办项。
3. 向用户简短汇报：共几轮；修了什么；哪些意见没改、理由是什么；哪个审查者无响应。
4. 不要合并 PR，等用户指令。
