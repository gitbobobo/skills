---
name: relay-audit
description: 分析近期 T3 Code 线程里人类的介入、agent 跑过的命令和各仓库新增的坏模式，按仓库找出人在充当传话员、agent 在走捷径或重复造轮子的地方，提出改进建议，并复盘已采纳改进的效果。只提建议，用户采纳后才建问题。仅限用户主动调用。
---

目标是提高你对 agent 的信任，把人从"传话员"的位置上撤下来。每次你纠正或插手 agent，都说明环境里缺了点什么。这个技能就是找出这些缺口，把它们补进环境里。

三条杠杆：给 agent 验证能力；收紧环境，让错误写法写不出来或过不了检查；把外部信息接进 agent 的工作循环。改法落在哪一层，按 [references/signals.md](references/signals.md) 里的五层顺序从强到弱选。代码库本身就是 agent 的记忆，它会照着已有写法扩写，所以要像园丁一样，在坏模式扩散之前清掉它。

这个技能只做诊断和建议。除了下面"状态目录"里的文件，以及用户采纳后建的问题，不修改任何仓库，不提交，不推送。

## 状态目录

`$RELAY_AUDIT_HOME`，默认 `~/.local/state/relay-audit/`。不要放进任何仓库，里面有对话摘录。

- `ledger.json`：所有建议及其状态，格式见文末
- `reports/<时间>-digest.md`：脚本生成的摘要
- `reports/<时间>-report.md`：每轮给用户的报告
- `issues/<项目>/<ID>.md`：本地 markdown 问题（没有 Fast Ship 项目和 GitHub 远程时才用）
- `rollups/<时间>.json`：每轮的命令与坏模式聚合。T3 切库时丢过历史命令，命令类的纵向对比只能靠这些快照，别删

## 判断用户这次要做什么

- 用户对上一轮的建议做了决定（"采纳 R-012""R-013 不要，因为……"），按"处理决定"做。
- 其他情况都是跑一轮审计，按"审计"做。

## 审计

### 1. 同步已采纳条目的进度

读 `ledger.json`。对每个 `adopted` 且关联了问题的条目，查问题状态：

- Fast Ship：`GET /api/issues/:id`，`state` 为 `closed` 或 `workflow_status` 为 `done` 即完成（调用方式见 fast-ship 技能）
- GitHub：`gh issue view <n> -R <owner/repo> --json state`
- 本地 markdown：看文件里的 `状态：` 行

完成的改为 `done`，写上 `doneAt`。不需要建问题的条目，由用户告诉你做完了才改。

### 2. 采集

```bash
node ~/.agents/skills/relay-audit/scripts/collect.mjs
```

默认从上次运行的 `lastRunAt` 采到现在，并带 14 天基线。终端输出复盘表、总览、环境快照和跨项目重复消息，最后两行是完整摘要和本轮聚合快照的路径。记下输出里的 `windowEnd`。

摘要文件里每个项目分这几节：环境（AGENTS.md、PR 模板、CI、lint 配置、仓库内技能、特性地图）、坏模式新增（默认分支上本期新增的类型逃逸、lint 豁免、临时方案注释、跳过的测试、吞掉的错误）、agent 命令（临时脚本、等待、手动起服务、编码保险、重建工作目录、反复执行的命令，以及**失败命令**聚类）、人类消息。坏模式统计基于根目录检出的 `origin/HEAD`，摘要里写了它的最后提交时间，太旧时先提醒用户拉取。

脚本报"数据库结构变了"时立即停止，告诉用户需要更新脚本，不要改用其他方式猜数据。

### 3. 复盘

对 `done`、`verified`、`ineffective` 的条目看复盘表：

- `doneAt` 之后不到一个完整采集周期：标"观察中"，不下结论。
- 本期频率比提出时的基线降了一半以上：改为 `verified`。
- 没降下来：改为 `ineffective`，在诊断步骤里查清楚为什么没起作用（没被触发？agent 没照做？改错了地方？），作为本轮建议重新提出。

### 4. 诊断

按项目读摘要文件的对应小节，不要一次读完整个文件。按 [references/signals.md](references/signals.md) 把信号归为七类。人类消息只能看到你插手的地方；agent 命令和坏模式能看到你没注意到的地方，两边都要看。

- 某条消息看不出原因时，用 `node <脚本> --thread <线程 ID 前缀>` 读完整上下文。
- 坏模式**先看「每百提交」那一列**，不要看每天：提交速率本身会浮动，提交多的一期每天的数字会整体抬高，看起来像扩散。每百提交明显高于基线的，才去仓库里看那几行代码，判断是不是真问题，并用 `git log -S` 找被复制的源头。惯用法（测试 teardown 的 `try?`、平台 API 逼出来的 `@Suppress`）不算，散在很多文件里各一两处通常就是惯用法，集中在少数文件才是被抄。
- 命令统计只到 T3 的留存下界，摘要会写明下界时间。看到「无可比基线」就别拿本期数字当增长，用绝对量和 `rollups/` 里的上一轮对比。
- **「失败命令」小节必看**，它是绕路最直接的证据，判读方式见 signals.md 第 7 类。注意失败按 `status` 判定（不是 exitCode），搜索工具的「无匹配」已单独计数、不算失败。
- **看线程数，不只看次数。** 散布在很多线程的摩擦是系统性的，集中在一个线程的多半是那次任务的特殊情况。每个命令类别、每条反复命令都标了线程数。
- 本期有合并 PR 的仓库，抽查两三个：`gh pr list -R <owner/repo> --state merged --search "merged:>=<本期起点日期>"`，看审查 bot 的意见和 diff。多个 PR 里出现同一类意见或同一种 workaround，就是约束缺口或坏模式扩散。只抽查，不逐个审。
- 提建议前先查实：去对应仓库看 AGENTS.md、PR 模板、lint 配置和已有技能，确认这个缺口真实存在。如果已经有对应的规则或技能，问题就变成"为什么它没生效"。
- 给每条建议定指标，记下基线频率：人类消息用 `node <脚本> --count "<正则>" [--project <项目>]`，agent 命令用 `--count-command "<正则>"`，坏模式直接用摘要里该类别的基线。正则要能匹配目标，又不误伤别的。`--count-command` 报「基线不可用」时，把本期速率记为基线并在条目里注明，不要当成 0。

### 5. 提建议

每轮最多 5 条新建议，按 signals.md 的排序规则选。上一轮还没答复的 `proposed` 条目不重新写，只在报告里列出 ID。已经 `rejected` 的不再提，除非对应信号的频率比拒绝时翻了一倍，这时要明确说明是重新提出、拒绝理由是什么、数据变了多少。

每条建议写清楚：

- 仓库（跨项目的写"全局"，落点通常是 skills 仓库）
- 问题类别
- 证据：出现次数、所在线程标题、一两句原话（摘要里已脱敏，引用前再确认没有密钥）
- 改法：具体到改哪个文件、加什么规则或脚本
- 落点层级：五层里的哪一层，为什么做不到更强的一层
- 是否需要改仓库文件
- 指标：用哪个正则或标签统计，基线多少/天，降到多少算有效
- 成本和风险：改动量；改错了能不能撤回

修改已有的技能或规则优先于新增。

### 6. 写报告，更新 ledger

1. 报告写到 `reports/<时间>-report.md`。
2. 新建议以 `proposed` 状态追加到 ledger，ID 接着最大的编号往下排。
3. 把 `lastRunAt` 设为这次的 `windowEnd`。报告写完才更新 `lastRunAt`，中途失败下次会重采同一段。

### 7. 回复用户

在线程里给出报告的精简版：

- 复盘：哪些改进验证有效，哪些无效、为什么
- 各仓库的信任状况：每个活跃仓库一行，说清它现在卡在哪（没有验证 CLI？没有特性地图？坏模式在增长？基线常脏？），以及下一步最该补什么
- 本轮建议：每条两三行，带 ID
- 待决定：本轮和之前未答复的 ID

结尾告诉用户怎么回复，比如"采纳 R-012、R-014；R-013 不要，理由……"。不要替用户决定。

## 处理决定

### 采纳

用户说了直接实施的条目，就直接改，不要建问题。改完在 ledger 里记 `done` 和 `doneAt`。改动小、你这轮就能连同验证一起做完的（改一行文档、调一个正则），主动问一句能不能直接做，别默认开问题。

其余需要改仓库文件的（代码、配置、AGENTS.md、PR 模板、技能都算），**每个条目只建一个问题**。下面三条是优先级降级链，不是三个步骤：从第 1 条往下找第一个适用的，建完就停，不要在第二处重复建。

1. **Fast Ship**：用 fast-ship 技能列出项目，用 `github_owner/github_repo` 匹配仓库的 git 远程。匹配到就在该项目建 internal 问题，不设 `workflow_status`。**建完即止，后面两条不再执行。**
2. **GitHub**：仅当上一条没有匹配到 Fast Ship 项目时才用。`gh issue create -R <owner/repo>`，先用 `gh repo view --json visibility` 查仓库是否公开。公开仓库的问题正文只写概括，不引用对话原话。**建完即止，第 3 条不再执行。**
3. **本地 markdown**：仅当前两条都不适用（没有 Fast Ship 项目，也没有 GitHub 远程）时才用，写到 `issues/<项目>/<ID>.md`，第一行写 `状态：待处理`。

一个条目同时涉及多个仓库时，仍然只建一个问题，建在改动主要落点的那个仓库，正文里写清其他仓库要配合改什么。

问题正文要能独立看懂，接手的 agent 不需要读本技能：

- 背景：哪类问题，出现了多少次，代表性原话
- 建议改法
- 验收：哪个指标降到多少；能写成可执行检查（lint、测试）的就写成检查
- 来源：relay-audit 的条目 ID

不需要改仓库的（比如调整用户自己的使用习惯、T3 设置），只在 ledger 里改为 `adopted`，说明由用户执行。

### 拒绝

改为 `rejected`，记下理由和拒绝时的指标频率。

### 暂缓

保持 `proposed`，不用改。

## ledger.json 格式

```json
{
  "lastRunAt": "2026-10-05T01:00:00.000Z",
  "items": [
    {
      "id": "R-001",
      "createdAt": "2026-10-05T01:00:00.000Z",
      "project": "musiver",
      "category": "传话 | 验证缺口 | 约束缺口 | 无效停顿 | 重复提示词 | 坏模式扩散 | 重复造轮子",
      "layer": "代码库和架构 | 静态分析 | 规则、审查 bot、技能 | 验证",
      "title": "PR 收敛后自动提示合并指令",
      "status": "proposed | adopted | rejected | done | verified | ineffective",
      "metric": { "kind": "message", "pattern": "合并PR，删除工作树", "projects": ["musiver"], "tag": null, "baselinePerDay": 1.8 },
      "issue": "Fast Ship 问题链接、GitHub 问题链接或本地文件路径",
      "reason": "拒绝或判定无效的理由",
      "doneAt": null,
      "history": [{ "at": "2026-10-05T01:00:00.000Z", "status": "proposed", "note": "" }]
    }
  ]
}
```

`metric.kind` 决定统计什么：

- `message`（默认）：人类消息。`pattern` 是正则；`tag` 可以是脚本打的标签（催促、纠正、粘贴、交给你做、调用技能），和 `pattern` 同时出现时两者都要满足。
- `command`：agent 执行的命令，含子代理线程。`pattern` 是匹配命令原文的正则。
- `garden`：默认分支上新增的坏模式。`pattern` 填类别名（类型逃逸、lint 豁免、待办与临时方案注释、跳过的测试、吞掉错误），`projects` 必填。

`metric.projects` 为空表示统计全部项目。每次改状态都在 `history` 里追加一条。

## 技能自身

脚本的标签和聚类不准、摘要漏了重要信号、某类建议总被拒绝，这些都可以作为一条针对 skills 仓库的建议提出来。
