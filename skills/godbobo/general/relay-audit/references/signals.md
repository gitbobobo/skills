# 信号对照表

摘要里的标签和计数是脚本按规则算出来的，只是线索。判断要看原文：人类消息看它前面那条 agent 回复，命令看完整输入，坏模式去仓库里看那几行代码。

## 落点：五层，从强到弱

不管是哪一类问题，改法都要落在下面某一层。能放在更强的一层，就不要放在弱的一层。每条建议都要写明选了哪一层，以及为什么做不到更强的那层。

1. **代码库和架构。** 改数据结构、模块边界、框架约定，让错误写法根本写不出来。比如只允许一种功能目录结构，用依赖图禁止某类导入。agent 会照着代码库里已有的写法扩写，所以代码库本身就是 agent 最可靠的记忆。
2. **静态分析。** lint 规则、类型约束、编译器诊断、CI 检查，在本地和 CI 都能拦住。看到坏模式时，第一反应应该是写一条 lint 规则先止血，存量可以以后再清理。
3. **规则、审查 bot、技能。** AGENTS.md、PR 模板、审查 bot 的配置、技能。这一层是引导，agent 可能没读到，驾驶 agent 的人也可能忽略它。
4. **风格指南和人工审查。** 只能靠人在审查时记住，PR 一多就守不住。这一层只适合用来发现缺什么，不适合当作改法。

验证是另一个维度，不在这条线上。它回答的是"做对了没有"，要给 agent 能自己拿到的实际证据。

## 七类问题

### 1. 传话：人在系统之间搬运信息

数据来源：人类消息。

识别特征：
- 粘贴审查意见、CI 报错、日志、截图、Issue ID、预览链接
- 在两个线程或两台设备之间转述进度，比如"PR #173 存在跨端漂移需要对齐"
- "检查下是不是改完了"，也就是替主代理去问子代理
- 用户去别的系统看了一眼，再回来告诉 agent 结果
- 用户给 agent 解释功能在哪、怎么操作才能复现

对应杠杆：外循环。让 agent 自己拿到这些信息。

改法，按优先级：
1. 已有技能或脚本没被触发，就查原因：没写进 PR 模板？技能描述没覆盖这个场景？agent 读了但没照做？然后修它。
2. 给 agent 一个能直接查到信息的命令或脚本，比如 `gh` 查审查意见、查 CI 日志的 CLI、跨设备共享状态的文件或 Issue。
3. 用户报告的问题说不清楚、agent 只能猜的时候，给应用建一份特性地图（见第 2 类）。
4. 交给定时任务或 webhook 去触发，人只看结果。一批相关的报告交给同一个协调 agent 统一处理，不要一条报告开一个 agent，这样能避免重复劳动，也更容易找到共同的根因。

指标：对应粘贴类消息的每日次数。

### 2. 验证缺口：agent 说做完了，其实没做完

数据来源：人类消息，加上 agent 命令。

识别特征：
- agent 报告完成后，用户指出功能、视觉或截图有问题，比如"gif 还是看不到弹框"、"截图无法显示"
- agent 让用户去验证："请你检查一下"、"刷新看看"
- 同一个问题来回修了三轮以上
- agent 说"无法截图""无法验证"就结束了
- 命令记录里，agent 每次都现场拼启动、截图、抓日志的命令（见第 7 类）

对应杠杆：验证。给 agent 手和眼睛，让它拿出能自己检查的证据。

一套好的验证由两部分组成：

- **CLI**：放在仓库或技能目录里，能稳定地启动应用、操作界面、截图、抓 trace 和性能数据。所有 agent 都用这一套，不要每个会话各写一份脚本。CLI 要持续投入维护，覆盖各种使用场景。
- **特性地图**：一份记录应用有哪些功能、用户怎么到达（快捷键、要点哪个元素）、每个功能该是什么表现的文档，放在验证技能或仓库里，并用自动化保持同步。有了它，agent 才能看懂含糊的报告，知道该验证什么。

改法：
1. 写验证 CLI 或补齐它缺的能力。
2. 建特性地图，并设好自动维护（比如合并 PR 后的自动化任务）。
3. 应用要能部署到一个 agent 可以随便折腾的环境里，比如独立的数据目录、测试账号、可重置的模拟器。
4. 验证结果要能被 agent 自己检查，比如截图后自己读图确认，GIF 抽帧确认关键状态出现过。
5. 正确性靠验证，质量靠技能。能量化的质量（性能、包体积）要让验证 CLI 输出数字，agent 才能爬山优化。

指标：同类纠正消息的次数，或者对应临时命令的次数（`kind: command`）。

### 3. 约束缺口：同一种错误反复出现

数据来源：人类消息、审查意见。

识别特征：
- 用户反复纠正同一种写法、命名、目录结构、依赖用法
- 代码质量审查（thermo-nuclear 等）连续几轮报同一类问题
- 审查 bot 在不同 PR 里反复提同类意见
- "清理基线上的既有编译、lint、测试错误"这种话经常出现，说明基线经常是脏的

对应杠杆：环境约束。按五层落点从上往下找能放的最强一层。

指标：对应纠正消息或审查意见的次数。

### 4. 无效停顿：agent 停在了不该停的地方

数据来源：人类消息。

识别特征：用户回了"继续""按推荐""确认""开工""需要"这类话，而且 agent 停下前说的是"确认后我开始实现""要不要我继续"，或者把计划列完就停了。

先区分两种情况：
- agent 有一个真实的决策点要问（比如 grilling 的提问、产品取舍），用户回"按推荐"是正常决策，不算问题。但如果用户对某类问题总是选推荐项，可以建议这类问题以后直接按推荐做，只在报告里说明。
- agent 本来可以接着做，只是习惯性停下来要确认，或者服务中断后需要人工"继续"。前者改 AGENTS.md 或技能里的停顿规则；后者属于 harness 稳定性，记下来但不作为仓库建议。

指标：标签"催促"的每日次数，可以按项目统计。

### 5. 重复提示词：同一段长话反复粘贴

数据来源：人类消息。

识别特征：基线加本期 3 次以上的同一段消息，尤其是多步骤的长指令。

改法：
- 2 个以上项目都在用：做成 skills 仓库（gitbobobo/skills）里的全局技能，或者合并进已有技能。
- 只有 1 个项目在用：写进该项目的 PR 模板待办或 AGENTS.md。
- 里面带变量（Issue ID、PR 号）的，技能接受参数，人只需要给变量。
- 一段提示词总是紧跟在某个事件之后发（比如 PR 收敛后总是发"合并 PR，删除工作树"），考虑让上一个流程结束时自动衔接，或者在上一步的结束汇报里给出一句话就能触发的指令。

技能写的是流程，不是实现细节。新模型用不着逐条命令，技能应该越写越短。

指标：该段提示词的每日次数（用 `--count` 加一段有代表性的原文定正则）。

### 6. 坏模式扩散：代码库在教 agent 走捷径

数据来源：摘要里的"坏模式新增"。

agent 会照着代码库里已有的写法扩写。一个看起来无害的临时方案或解释性注释，几天到几周内就会被复制到各处，变成事实上的标准写法。注释尤其危险：agent 会拿旁边的注释当理由，用临时补丁绕过问题而不去解决它。

识别特征：
- 某类坏模式（类型逃逸、lint 豁免、临时方案注释、跳过的测试、吞掉的错误）本期的每日新增明显高于基线
- 新增集中在少数几个文件，或者同一种写法出现在多个不相关的模块
- 抽查合并的 PR 时，看到多个 agent 用了同一种 workaround

诊断时去仓库里看那几行代码，判断是不是真问题（测试里的 `try?` 可能是合理的）。用 `git log -S '<片段>'` 找到最早出现的地方，那往往就是被复制的源头。

改法，按顺序：
1. 写 lint 规则禁止这种写法，先止住增长。
2. 建一个清理存量的问题，让 agent 把代码库恢复到"被照抄也没关系"的状态。
3. 如果这种写法是因为缺一个正确的抽象（比如缺统一的错误处理），补上这个抽象，让正确写法成为最省事的写法。

指标：对应类别的每日新增（`kind: garden`，`pattern` 填类别名）。

### 7. 重复造轮子：agent 每次都在现搭工具

数据来源：摘要里的"agent 命令"。

识别特征：
- 临时脚本：`python3 - <<`、`node -e` 现写现用，内容每次差不多
- 手搓超时：`perl -e 'alarm'` 这类包装，说明环境缺一个可靠的超时或等待手段
- 长时间 sleep 等待：sleep 几分钟再看日志，说明缺一个"阻塞到完成为止"的命令
- 手动起服务：每次自己拼配置、起进程、curl 探活
- 某个命令前缀反复出现或反复失败
- 环境摩擦：每条命令都要带的 `chcp`、`OutputEncoding`、`cd /d <工作树>`。这不是 agent 的选择，是环境缺省值不对，让它自费买保险

**先看摘要里的「失败命令」小节，那是绕路最直接的证据。** 判读方式：

- `Command timed out after Nms` —— 不是命令坏了，是缺一个会阻塞到完成、带进度输出的入口。轮询日志（`Start-Sleep` 后 `Get-Content -Tail`）必然撞超时，应该换成等待脚本。
- 报错是 `unterminated string literal`、`系统找不到指定的文件`、参数被按空格拆开 —— shell 引用写错，不是代码问题。多见于 `cmd /c '...'`（cmd 不认单引号）和嵌套 `\"`。这类错误有时报错、有时**静默执行成别的东西**，后者更危险，看到一次就要当系统性问题处理。
- 报错是找不到 `Cargo.toml`、缺产物、路径不存在 —— 环境或工作树约定不一致，查是不是有两套目录约定。
- 同一条命令在**多个线程**失败，才是环境问题；只在一个线程里失败多半是那次的写法问题。

**跨线程数比次数更重要。** 一个摩擦出现 500 次但只在 1 个线程里，是某次任务的特殊情况；出现 100 次但散布在 25 个线程里，是所有 agent 都在踩的系统性缺口，优先级更高。摘要里每个类别和每条反复命令都标了线程数，`--count-command` 也会打印。

对应杠杆：确定性的部分交给代码，判断留给 agent。agent 每次都重新搭一遍，不仅浪费上下文和时间，每次做法还不一样，结果也没法比较。

改法：
1. 把反复出现的操作做成仓库里的命令（比如 `pnpm verify ios`、`make e2e-up`），或者放进技能的 `scripts/` 目录。
2. 等待类操作做成会自己阻塞、有超时、结束时打印结果的命令，取代 sleep 轮询。pr-review-loop 的等待脚本就是一个例子。
3. 反复失败的命令，查是环境问题（缺依赖、端口冲突、权限）还是 AGENTS.md 里写的用法过时了。

指标：对应命令的每日次数（`kind: command`，用 `--count-command` 定正则和基线）。

## 不算问题的情况

- 提出新需求、描述想要的效果、做产品决策
- 回答 grilling 等技能主动提出的设计问题
- 审美和体验上的主观反馈（"按钮应该右对齐"）。但同一类反馈反复出现时，可以变成设计规范写进仓库
- 第一次调用某个技能
- 读文件、查状态这类只读命令的重复
- 写 PR 描述、回复正文这类必须先写进临时文件再提交的操作

## 排序

优先级 = 出现次数 × 每次的代价 ÷ 改动成本。

- 每次的代价：一句"继续"按 1 分钟算；需要你去别处查信息再回来的按 5 到 10 分钟算；需要你手动验证的按 10 分钟以上算。agent 侧的浪费（临时脚本、sleep）按它拖慢的时间和带来的不稳定估算。坏模式扩散按它被复制的速度估算，越早止血越便宜。
- 改动成本：改一段文案 < 加 lint 规则 < 写脚本或 CLI < 改架构。
- 同等优先级下，先选能同时惠及多个项目的，再选让上下文很少的 agent 也能做对的。
- 覆盖的线程数和项目数是优先级的放大器：同样的次数，散布越广越该先修。只影响单个线程的，除非代价极高，否则往后放。
